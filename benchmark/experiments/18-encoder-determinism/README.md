# 18 encoder determinism

2026-09-13. the release manifests promise that the same recipe and the same toolchain give the same file_hash. this checks the part of that promise a reviewer can break without changing either: the number of workers the encoder gets.

hypothesis: on one toolchain, the three backends write the same bytes whatever the worker count; a release rebuilt on a machine with more or fewer cores hashes the same, and the toolchain record in the manifest is the whole of what reproducibility depends on.
method: benchmark/tools/encoder_determinism.py on 256 cards (every eighth id of sample-2048), the forge's own parameters per backend; av1 through encode_av1 with lp 1, 2, 2 again, 8 and 16; avifenc -q 48 --speed 6 --yuv 420 with -j 1, 8, all and all again, then an extra sweep at -j 2, 3, 4, 16 and 1 on the same letterboxed pngs; cjxl --lossless_jpeg=1 with --num_threads 1, 8, and the default twice; sha256 over the mp4 (av1) or over the concatenated per-image outputs (avif, jxl), plus a per-image comparison in the avif sweep.
verdict: refuted for avif, confirmed for the other two. svt-av1 gives one hash across lp 1 to 16 and cjxl gives one hash across thread counts, but libaom writes different bytes with one worker than with two or more: all 256 files differ between -j 1 and -j 2, and -j 2, 3, 4, 8, 16 and all are byte-identical to each other, 3.7 kB apart over the set. avifenc's default is -j all and the forge did not pass -j, so since #137 made avif the stills profile, the stills release hashed differently on a one-core machine than on any other. urna #139 pins -j 8 and records it.

the av1 result i expected, because the forge already pins lp=2 and svt-av1 documents its determinism at a fixed lp. cjxl in transcode mode is a lossless repack of the jpeg's coefficients, so thread count changing the bytes would have been a bug. avif was the one i had not looked at, and it is the backend that just became the default for stills.

the shape of the avif result matters more than the size. it is not noise across runs, two runs at -j all agree to the byte. it is a two-class split: one worker takes a different path through libaom than two or more, probably the row-multithreading or tile decisions the encoder makes when it knows it has help, and every image lands in the other class. the difference is small, 3.7 kB over 7.55 MB, and it is systematic, which is the worst kind for a reproducibility claim: a reviewer on a small vm gets a file whose sha256 does not match the release and has no way to tell why from the manifest, because the manifest did not record the thing that changed.

what this does not cover is the part the critique on the dataset card was actually about. one machine, one version of each encoder. i cannot say from here whether svt-av1 4.2 on x86 avx2 writes the same bytes as on arm neon, or whether libaom 3.16 will, and the honest reading of the release manifests is that file_hash reproduces under the recorded toolchain on this class of machine and is a claim under test everywhere else. the tool is in the repo so the next machine can run it against these hashes.

provenance: apple m4, macos 26.6.2, ffmpeg 9.0.1 with svt-av1, libavif 1.4.2 with aom 3.15.0, cjxl 0.12.0, forge from the urna #138 branch (the encoder code is unchanged from main there). raw json under `data/`; wall seconds were taken while the five-model build held the gpu and are not a speed measurement.
